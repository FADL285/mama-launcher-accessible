## Decisions (owner)

### D-01 (DECIDED 2026-11-12) - Short-number policy: option C

**Decision (owner, 2026-11-12):** in the dialpad only, Call is enabled for input of **3+ digits or any input containing `*` or `#`**; input of **1-2 plain digits and a lone `+` is truly disabled** - greyed, `setEnabled(false)`, TalkBack announces disabled. **Save follows the same rule** (its handler already gates <3 at `DialpadActivity.java:49`; align its enabled/a11y state and threshold with C). Visual state, accessibility enabled state and handlers must agree for every input.

Settled scope notes (from the review discussion):
- The rule lands in `DialpadActivity` before `callAction.tap(...)`, never in the shared `DirectCallAction` (which also serves history and contact confirmation). See T-05.
- Emergency numbers are unaffected by the rule **for Egypt**: Egyptian emergency numbers (122/123/180) are 3 digits, so they stay callable under C, and on most Android builds `ACTION_CALL` to an emergency number opens the system dialer instead of calling. Region note (review): countries with 2-digit emergency numbers (e.g. France 15/17/18) would have them blocked by C before the system dialer is reached; if supported regions ever expand beyond Egypt, the owner must add an explicit exception list first.
- MMI/USSD strings such as `*#06#` are callable under C (they contain `*`/`#`); `#` encoding goes through `dialUri` (`DialIntents.java:31`) as today.
- Empty input stays non-callable in all cases.

Background for the implementer: today the dialpad dims Call/Save below 3 characters via alpha only (`DialpadActivity.java:215-217`; neither button is disabled, so TalkBack announces both as enabled at every length) while the Call handler accepts any non-blank input (`DirectCallAction.java:18`).

### D-02 (DECIDED 2026-11-12) - Favourite semantics: the star belongs to the contact (option a)

**Decision (owner, 2026-11-12):** the star belongs to the **contact (the name), not to a number**. Removing the star from any number of a system-starred contact unpins the whole contact with all its numbers; starring any number pins the contact. (Owner's words: the star is on the name - if a name has several numbers, the star is on the name and removing it removes it for all its numbers.)

Background for the implementer: local favourite overrides are stored **per number** today (`LocalFavorites.java:7-8`), but a contact is pinned when **any** of its numbers is a favourite (`LocalFavorites.java:10-12`), with the system star as the default. So un-starring number A of a system-starred contact with numbers A and B stores `false` for A only; B still defaults to the system star and the tile stays pinned, which is exactly the confusion this decision removes. The launcher never writes to the system contacts provider; the Contacts-app star stays the default for contacts with no local mark. Migration of existing per-number local marks is part of T-16.

Settled sub-points (from the multi-number re-review; recorded as defaults the owner may still override before implementation):
- The star stays **gated behind a visible number choice** on the confirmation screen (consistent with "nothing actionable until a visible choice"); only its hint wording changes to per-contact language. The Call button stays gated exactly as today.
- Contact identity for local marks stays `CONTACT_ID`; a documented known limit: Android can change `CONTACT_ID` when raw contacts are joined or split, which can orphan a local mark (`LOOKUP_KEY` is the stable reference but is not loaded today, `ContactsLoader.java:80-88`). Widening to `LOOKUP_KEY` is out of T-16's scope.

### T-06 (P3) - Bounded, cancellable contacts pipeline (GPT-03 / CL-03 / A03)
- **Goal:** contacts reads are owned, coalesced, cancellable and deadline-bounded; history renders number-only results without waiting indefinitely for optional contact labels.
- **Scope:** shared contacts boundary absorbing all four current consumers with their different threading models: `PhoneActivity.java:92` (raw thread), `DialpadActivity.java:39,51` (activity-owned `lookupWorker`), `HistorySnapshot.java:54-62` (signal checked only after the full load), `ContactsLoader.java:90-98` (query and loop without `CancellationSignal`). Follow the existing budget-plus-signal pattern in `CallLogRepository.java:37,74,119` as the design model.
- **Degraded history (review):** define behavior for both rendering and opening a row: valid history renders number-only when labels are late/unavailable; tapping a callable row reaches number-only confirmation with the exact raw number; retries never grow an unbounded queue; late labels cannot reopen a paused/replaced screen; coalescing must not cancel another live consumer (grid vs dialpad refresh/Save vs history). - **Non-goals:** changing failure-vs-empty semantics (a deadline expiry maps to **failure**, e.g. the Save path's `dial_lookup_needed`, never to "empty"), the exact-clicked-number rule, the 200-row paging contract, provider write access.
- **Acceptance/tests:** a **named deadline value** and where it is configured; latch-controlled overlapping refresh/pause/destroy; blocked provider with valid call log; repeated retries; large result sets; cursor close and permission loss; repeat T-04 measurements against the target-to-beat.
- **Risk:** medium (concurrency). **Effort:** ~3-5 days (review-revised from 2-4; four call sites with different lifecycle contracts). **Depends on:** T-04 baseline. Lands before T-07 (both touch `PhoneActivity`).

**Recreation (implementation review):** the user's place also survives activity recreation (config change or process death): the opened contact and the first visible contact are saved in instance state and restored on recreate; a saved position is consumed only when actually applied, and a stale refresh from before the restore cannot re-apply or overwrite it (refresh-generation guard).
- **Risk:** low. **Effort:** small (~half day). **Depends on:** none standalone; subsumed by T-06 when that lands.

### T-14 (tiny) - PIN lockout deadline clamp (CL-09)
- **Goal:** a backwards device-clock change cannot extend an active PIN lockout beyond the 10-minute cap.
- **Scope:** the deadline is stored as `System.currentTimeMillis() + lock` (`PinGateActivity.java:203`) and checked with `until > now` (`PinLock.java:87-89`) with no upper bound on `until - now`. Required fix (review): a **monotonic elapsed-time deadline** - persist `elapsedRealtime` at arming plus a boot reference (e.g. also persist the wall-clock elapsed snapshot and refresh it on each gate entry) - so a backward jump smaller than the cap cannot extend a lockout either. A wall-clock clamp (`until - now > MAX_LOCK_MS` treated as expired) is defense-in-depth only: a 9-minute-elapsed lockout followed by an 8-minute clock rollback stays within the cap yet lasts 18 real minutes, which the clamp alone does not catch.
- **Non-goals:** changing lockout durations or failure thresholds; forward clock changes ending a lockout early (harmless for a convenience PIN).
- **Acceptance/tests:** a stored deadline far in the future relative to now unlocks after at most `MAX_LOCK_MS`; a stored deadline carrying no anchors (written by an older version, or corrupted prefs) is not an eternal lockout: on read it is re-armed to now + `MAX_LOCK_MS` and persisted with fresh anchors, then counts down normally; the sub-cap rollback case (9 minutes elapsed, clock moved back 8) still unlocks on schedule; reboot during lockout handled via the boot reference; ordinary lockout durations still apply; existing PIN tests unchanged.
- **Risk:** low. **Effort:** tiny (~2 hours). **Depends on:** none.

### T-17 (small, Low) - Dedup national/international forms of one number on a contact
- **Goal:** a number saved twice on one contact in national and international form (e.g. `01001234567` and `+201001234567`) shows as ONE button, so mama never chooses between twins that dial the same person.
- **Scope:** `ContactsLoader.group` dedups only by stripped digits and one leading `+` (`ContactsLoader.java:36-43,60`), so those two forms survive as two buttons, contradicting the "never choose between twins" intent (`:45-47`). Dedup with the E.164 equivalence `DialContactMatcher.exact` already uses (`DialContactMatcher.java:20-27`, country from `NumberRegion`). "First-seen" is NOT a valid survivor rule: the provider query uses a null sort order (`ContactsLoader.java:90`), and the pre-existing digits-only collapse keeps the first-seen row (`ContactsLoader.java:60`), so the survivor rule must run over the WHOLE equivalence class (digits-equal and E.164-equal forms grouped first, one pick per class) - otherwise provider order leaks through the early collapse. The survivor is chosen by a fixed, total, order-independent rule: **rank national first (no `+` AND no `00` international prefix), then the `+` form, then the `00` IDD form; within a rank prefer fewer normalized digits; then lexicographic on the normalized form, then on the raw string, then on the label** (the last tie-break makes identical raw numbers with different labels deterministic too). "National" is defined positively so an IDD form like `0020100...` can never outrank the national `0100...`. The surviving number keeps its own type label (the dropped form's label is dropped with it - stated so no label vanishes silently). **Roaming trade-off (owner-acknowledged):** preferring the national form means a phone abroad on an Egyptian SIM would dial `0100...` rather than `+20...`, which generally does not connect outside Egypt; accepted for a home-bound user, and it preserves today's display and dialling behaviour. Reproduced by the multi-number re-review: `01001234567`, `+201001234567` and `0100 123 4567` on one contact grouped to two buttons; only the spaced variant collapsed.
- **Non-goals:** merging different numbers; changing the display form shown (the survivor rule only makes today's arbitrary choice deterministic); cross-contact matching (the same number under two names stays two tiles - verified correct).
- **Acceptance/tests:** the three-form fixture collapses to one button under ALL SIX row permutations, including the spaced variant first (catches an early first-seen collapse); genuinely different numbers on one contact are untouched; short numbers that fail E.164 validation (<7 digits) keep today's digits-only behaviour; the national form wins when national / `+` / `0020` forms are all present; the surviving number's own label is kept; an identical raw number with two labels picks one label deterministically in both orders; grouping order otherwise preserved; concrete service-string rows (`123` vs `*123#`, and distinct `*`/`#` strings) are never treated as phone-number equivalents; Unicode/Arabic-Indic digit forms of the same digit sequence DO dedup (verified: `DialContactMatcher.digits` maps any Unicode decimal digit via `Character.digit`) and the ASCII form survives, region-free - this is a stated change from today, where they show as two buttons; national/international Unicode equivalence remains region-dependent; region rows split a known non-EG fallback region (both forms stay) from a genuinely unknown region (only digit-identical forms merge). Regression (Greptile): a local star made on the form that dedup removes must still pin the contact - with T-16's contact-level key this is structural, but keep the explicit test.
- **Risk:** low. **Effort:** small (~half day). **Depends on:** T-16 (its contact-level key makes the kept-form choice star-safe; dedup before that could hide a favourite marked on the removed form).
